## 04 研究内容

本课题拟以团队主导的开源底座 BrewFS 为基础，围绕统一文件视图组织 Nydus EROFS、lazyload、Checkpoint/Restore 与并发创建机制。下述新增格式、接口与策略均为拟研究内容，性能目标不视为已有沙箱启动实测，引用底座实测时注明来源。

### 内容一：统一镜像—工作区数据格式

镜像层与工作区增量分别管理，容易造成创建时重复复制、恢复时版本错配。本研究拟将 Nydus EROFS 镜像层接入 workspace overlay，作为不可变 packed lower；Agent 对运行时文件和工作区的修改归入私有可写 upper。fork 从精确 revision 创建，仅写基线引用、元数据头与新的可写头，不复制 clean 数据、不遍历目录树，实现 O(元数据) 而非 O(数据) 的创建；这里的元数据指创建必需的头部记录，不是全树元数据。

拟扩展 manifest，记录格式版本、必需特性、OCI layer digest 链、EROFS 对象 digest、root inode 和映射索引。导入器核对层次顺序，将 OCI whiteout 和不透明目录转换为 tombstone 与目录回落边界；挂载器核对 manifest 摘要、root inode 类型及索引边界，读取对象时按摘要校验，拒绝跨版本拼接。摘要校验依赖可信的 revision 引用，不把摘要本身当作来源认证。兼容版本只追加可选字段；改变语义时生成新 revision，经双读比对后切换。旧二进制遇到未知主版本或必需特性须拒绝挂载，延续 workspace-v1 不回落 flat 行为的边界。

命名空间查询先查 upper：命中有效条目即返回；命中 tombstone 即报告不存在；只有未命中且允许回落时才查 lower。拟以镜像 digest 与 EROFS inode 标识建立稳定映射，使硬链接在同一工作区指向同一逻辑 inode。extent 索引把文件逻辑区间映射到 EROFS pcluster 的压缩对象区间，或 upper 的数据 slice。BrewFS 的 64 MiB chunk、4 MiB block 是数据组织粒度，pcluster 是压缩单元，二者不等同；跨边界读取须定位涉及的 pcluster，再组装目标字节，不能按 BrewFS 块号直接计算压缩偏移。

copy-up 拟只建立 upper inode 与修改区间，保留未修改区间的 lower 引用。文件大小内的读路径依次检查 upper extent、`lower_visible_size` 限定的只读基线、空洞零值。缩短文件时，在同一事务中缩小该边界并裁剪 upper extent；再次扩展也不扩大基线边界，防止已截断内容复现。局部覆盖仅补读必要基线区间，避免为小写入复制整个文件。

预期形成可校验、可拒绝不兼容版本的格式契约。以 xfstests、pjdfstest 和故障用例验证删除后重建、硬链接、跨压缩单元读及截断后扩展，检查 fork 写入量是否随镜像容量增长。对蚂蚁的价值是减少 containerd 镜像准备和 runD 工作区创建中的复制与遍历，结合下述 lazyload，以创建路径传输字节减少 ≥90% 为目标，分别核算元数据、数据和校验开销。

### 内容二：EROFS 语义下的按需加载与元数据预热

随机小读的首次访问可能被压缩单元解码与大块拉取放大，提前填满缓存又会挤占其他 Agent 的工作集。本研究拟建立“按需 range read—私有 lookahead—复用后提升”的路径：lower 按 extent 索引请求必要 pcluster，upper 按 64 MiB chunk、4 MiB block 定位不可变对象及所需区间。解码器检查长度、边界和校验信息，仅返回目标逻辑字节；读取放大量包含压缩对齐带来的额外传输。为避免整对象摘要迫使全量读取，拟在受 manifest 摘要保护的索引中保存压缩单元及 upper slice 的分段校验值；读取器取齐对应校验区间后验证，校验失败的数据不得进入缓存。

对已触达压缩单元，解码后的相邻字节先存入该 workspace 的有界私有 lookahead，顺序访问可直接复用；不因一次缺失就拉取整个 chunk。预读器拟根据连续访问和消费比例调整窗口，收益不足即收缩或停用。共享缓存准入器只有观察到区间复用，才考虑提升完整 BrewFS 块；涉及 lower 时，提升表示补齐对应逻辑块所需的 pcluster 集合，不改变压缩粒度。每个 Agent 的数据物化由实际触达驱动，其余块保留在对象存储；预测读取与块提升的额外字节单独计账。

读路径先由 Linux page cache 判定；未命中进入 FUSE 后，BrewFS 依次检查内存缓存、SSD 缓存，再发起 OSS 请求，私有 lookahead 在内存层检查。共享缓存键绑定不可变对象 digest、区间和编码版本，组装后的逻辑块另绑定文件 revision 与 extent 摘要，防止同路径不同版本串读；upper 的未提交数据只在所属工作区可见。相同对象区间的并发缺失拟合并为在途请求，共享校验后的结果。实验将联动调整 FUSE `max_read`、kernel io_pages 及预读窗口，测量请求合并减少的往返与首次读取增加的传输、解码和排队，避免只凭命中率选参。

attach 阶段拟常驻已验证 manifest，预取 root inode、启动路径索引页及必要映射，不扫描全量目录。缓存为空时先取这些必要元数据，其耗时计入冷启动；已有常驻索引的结果另报。以 attach 达到毫秒级为目标，记录首次 read p99、各级命中率、OSS 请求数和读放大，使用 fio 与启动轨迹对照立即整块提升、关闭预读等策略。对蚂蚁的价值是缩短 OSS 挂载和首个任务读取链路，以 4G 镜像无本地缓存冷启动由课题参照约 10s 降至约 1s 为目标，按实际传输字节验证节省；已有缓存吞吐仅支撑可行性分析，不能替代冷 OSS 测量。

### 内容三：Checkpoint/Restore 的一致固化与快速恢复

恢复速度取决于快照能否直接寻址，恢复正确性则取决于文件视图与执行状态是否来自同一检查点。本研究拟由 runD 协调暂停执行并阻止新文件写入，BrewFS 排空在途操作，在持久化屏障后固定文件 revision，再由 runD 完成配套执行状态固化，以共同 checkpoint 标识关联各部分。

| 状态类别 | 拟固化的数据布局 | 恢复责任 |
| --- | --- | --- |
| 镜像 lower | manifest、digest 与 root inode 引用，复用不可变 packed lower | BrewFS 校验并 attach |
| upper 增量 | 冻结文件增量组织为 Nydus EROFS 增量包，伴随保存 inode/extent、tombstone 与 `lower_visible_size` | BrewFS 重建文件视图并创建私有可写 upper |
| 执行状态 | runD 导出的进程、内存及相关状态对象，与文件 revision 共同登记 | runD 校验兼容性并恢复进程、内核与网络状态 |

固化器拟复用可引用的不可变对象，必要重打包在发布前完成。恢复时将冻结增量叠加到原 lower，组成只读检查点基线；日常 upper 写入无需逐次封存或轮转 head。fsync 成功须意味着相应数据对象已持久化至 OSS、校验通过且相关元数据事务已提交，不能以写回 staging 接收代替；目录项变更按目录 fsync 语义落实，检查点屏障覆盖全体待提交命名空间操作。rename、tombstone 与 extent 更新保持原子命名空间事务。发布器确认全部文件及 runD 状态对象可读取、摘要一致后，才以事务发布可见 checkpoint 版本。若中途崩溃，读者只能看到旧版或完整新版；未发布对象进入待回收集合。

恢复拟先解析并固定 checkpoint，校验格式及 runD 兼容性，由后端授予 lease 并推进 generation，再 attach 文件视图、创建可写头，最后由 runD 恢复执行状态并解除暂停。BrewFS 从对象存储直接恢复挂载，无需本地完整下载、解压；后续文件读取经 lazyload 解码必要区间。进程、内核及网络状态由 runD 负责，其必需状态装载时间计入端到端结果，不假定 runD 已支持全部内存按需恢复能力。

lease + generation fencing 拟在每次元数据提交和快照发布时由后端原子核验所有权、有效期与代次，确保每个 workspace 的写者唯一；租约失效即停止写入，拒绝 stale mount。旧挂载即使上传了对象，也不能发布可达引用。恢复器在索引检查或按需读取时发现 dangling extent 须报错而非补零；GC 以已发布快照、活跃 workspace 和在途上传 pin 为存活根，标记后再次检查版本与引用。删除候选须经事务进入回收状态，并与新增引用、恢复 pin 互斥；上传前登记 pin，未发布且无 pin 的孤儿对象经安全等待后回收，避免检查与删除之间发生引用竞态。

预期通过上传中断、发布崩溃、租约换代和 GC 交错注入验证一致性。对蚂蚁的价值是省去快照全量下载与本地解压，并复用运行时状态；以快照启动 100ms 级为目标，分别记录预热条件、无缓存恢复、固化排空时间及下载字节，明确收益与成本边界。

### 内容四：高并发创建的长尾抑制与池化预热

批量创建容易与写回、compaction、GC 竞争 CPU、连接和内存，单请求优化未必能降低整批长尾。BrewFS 在 2026-09-22 阿里云对齐评测中的随机写 p99 为 463.471 ms，表明前台写尾延迟仍需优化。本研究拟围绕创建关键路径实施资源隔离与分层预热。底座 workspace overlay 仍是可选功能，运维工具链尚在成熟；拟先固定 Redis/TiKV catalog 的事务语义和故障恢复接口，再接入宿主机侧 workspace 服务或 runD guest 内 FUSE 挂载，以同一检查点协议验证两种部署路径。

调度器拟分别设置前台创建、必需读取与后台维护队列，按 workspace 公平分配执行份额，并为前台预留连接和内存。后台任务受并发额度及可抢占执行片段约束；写回积压时对产生脏数据的工作区背压，保护创建预算，同时保证后台最低推进能力，避免积压反噬。fsync 需要的持久化不能被隔离策略绕过，其等待须计入请求时延。

元数据层拟将单操作涉及的多行更新批量提交，再对独立 workspace 采用 grouped publication，合并 RPC 与提交往返；组内逐项检查 revision、lease 和 generation，失败后按请求幂等键重试。限制组批等待，保持各工作区的原子可见性，不能为凑批延误低负载请求。控制面拟合并重复版本查询及挂载参数传递，并行准备相互独立的存储、网络和日志资源，保留所有权校验与失败回滚。

池化拟按镜像元数据、lower attach、guest 内核、运行时资源分级选择；网络与存储资源按可安全重置的单元复用。镜像相关项按 digest 与配置匹配，认领时创建独立 upper、取得新租约并重置身份，防止残留状态跨沙箱传播。预热器记录内存占用、补池成本、命中及耗尽回退；无缓存组清除镜像相关预热项并披露通用池状态，预热收益单列。针对 containerd 高并发 GC 抖动，拟在其接口允许范围内复用不可变内容引用、合并生命周期更新，并将非紧急回收错峰限流；持续核算待回收空间，避免以积压掩盖停顿。

预期以单机 100 个沙箱并发创建无明显长尾为目标。自建 benchmark harness 对照资源隔离、组批及预热的消融组合，在后台写回和 GC 压力下记录 p50、p99、最大值、失败率与整批完成时间。对蚂蚁的价值是减少控制面至 containerd/runD 的重复 RPC、提交和资源初始化，并降低后台干扰；按每次创建节省的事务数、CPU 时间及尾延迟量化收益，同时报告池耗尽和异构镜像场景的退化。
