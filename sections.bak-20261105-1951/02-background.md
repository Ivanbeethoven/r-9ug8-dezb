## 研究背景与问题分析

AI Agent 沙箱启动的主要矛盾是整条创建链路重复准备数据与运行状态，而镜像加载、状态恢复及资源调度缺少共同的数据视图和生命周期约束。

### 工作负载与启动链路

依据课题原文，Agent 代码执行、工具调用与任务隔离依赖沙箱，其短生命周期使创建开销直接侵占有效执行时间；依赖复杂扩大镜像体积，快速扩缩容增加无缓存节点，批量拉起则把平均时延问题放大为排队与尾延迟问题。因此，分析应从管控请求进入系统持续到任务可执行，而不能止于镜像挂载成功。

按逻辑依赖，完整链路为：管控请求下发 → 调度 → containerd 创建 → 镜像准备 → runD 运行时启动 → OSS/存储挂载 → 网络设备初始化 → 日志初始化。该顺序用于识别责任与阻塞点，实际实现中无依赖的准备可并行，不能把逻辑链条误当成必须串行的执行顺序。

| 环节 | 为什么慢：机制与阻塞位置 |
| --- | --- |
| 管控请求下发 | 请求解析、鉴权、API 转发及状态持久化构成控制面往返；原生 K8s 链路较长，多次事件传递与状态协调使节点收到创建指令前已有等待。 |
| 调度 | 节点资源与约束匹配、队列等待和绑定确认占据关键路径；若调度不知道镜像块、快照与资源池的位置，可能把任务交给数据未就绪的节点。 |
| containerd 创建 | 创建请求涉及运行时插件、元数据更新及 RPC；突发并发会竞争锁和队列，GC 又与前台操作争用 CPU、I/O 与元数据资源，形成批次性抖动。 |
| 镜像准备 | 传统 OCI 路径先完整拉取再解压，网络传输与解压写盘均随镜像体积增长；只触碰少量文件的任务仍须等待未使用的数据。lazyload 若未预热目录与索引，又会把成本转成串行小读。 |
| runD 运行时启动 | 从零准备执行环境、初始化资源并启动 guest 内核，重复支付系统引导及运行时初始化成本；缩短镜像读取不能直接省去这些计算与设备准备。 |
| OSS/存储挂载 | 身份与后端连接准备、挂载建立、元数据查询和首次数据读取包含远程往返；运行时就绪后才串行执行会继续累加等待，冷缓存放大首次访问成本。 |
| 网络设备初始化 | 网络命名空间、设备及配置需要主机侧资源操作；逐实例重复准备增加系统调用，并发下可能触发内核锁争抢，串行等待还会阻塞应用可达。 |
| 日志初始化 | 日志文件、流、采集通路与后端连接的准备占用元数据及 I/O；若同步完成全部初始化才发布就绪，后端排队或写回压力也进入启动时延。 |

上述因素归为五类开销：全量数据搬运与解压、运行时从零初始化、外围资源串行准备、控制面传递与调度等待，以及并发下的锁竞争、RPC 排队和 GC 干扰。它们会相互放大：镜像读取延迟使请求积压，积压又增加元数据与运行时竞争。表中机制来自课题问题描述及链路分析，不代表已获得蚂蚁内部各阶段耗时。

### 根本缺口：分别设计导致状态与视图脱节

课题明确指出：**镜像按需加载与运行时状态快照恢复分别设计，缺少统一数据格式、恢复链路与调度协同机制。** 镜像系统定位静态文件块，快照系统记录执行状态；若双方没有共同版本身份，恢复的进程可能引用与内存状态不对应的文件，或者需要额外复制、解压、重新挂载才能重建原路径。各自管理缓存和回收生命周期，还可能导致启动重复拉取、快照依赖被提前回收，以及调度无法识别可复用状态。

该缺口不仅影响速度，也涉及正确性。快照发布前若仍有相关脏数据未持久化，进程状态与文件视图便可能不一致；删除工作区若不检查活跃租约，会破坏仍在运行的实例；所有权变更后若旧挂载继续写入，则可能污染恢复结果。单独增加带宽、缩短镜像下载或扩大预热池，都不能给出这些跨组件约束。

### 文件系统视图作为统一抽象的依据与边界

镜像提供只读文件集合，运行过程产生可写增量，快照恢复则要求重新获得与执行状态匹配的文件集合。因此，稳定命名空间及其版本，比某次镜像下载更适合作为三者共同引用的对象。BrewFS 的 workspace overlay 已由不可变 packed lower 与私有可写 upper 构成：精确 revision 固定基线，manifest、digest 与校验确定内容；未命中 upper 时回落到 lower，显式 tombstone 抑制已删除条目重新出现；fork 只建立增量元数据与新的可写头，不复制 clean 数据或遍历复制目录树。

该结构为 Nydus EROFS、lazyload 与 Checkpoint/Restore 提供可对接的视图身份，并允许调度以相同身份判断数据与状态是否就绪。lease + generation fencing 约束单写者和失效挂载；快照、缓存引用与回收则需要围绕同一版本建立协同规则。统一格式不等于把可写状态直接塞入只读镜像：活动增量由 upper 承载，封存时再建立可校验的恢复版本；BrewFS packed 格式与 Nydus EROFS 的实际映射尚需研究。

BrewFS 只隔离文件视图，进程、网络、权限及 guest 状态仍由 runD 等上层组件管理。可对接宿主机 workspace 服务、guest 内 FUSE 挂载及 OSS 后端，但跨组件一致快照、恢复适配与资源协同尚未完成。workspace overlay 仍为可选功能，运维工具链仍在成熟；2026-09-22 阿里云对齐评测中，BrewFS 随机写、混合写 p99 分别为 463.471ms、492.831ms，前台写尾延迟仍是明确短板，不能用平均吞吐替代创建长尾分析。

对蚂蚁的具体价值在于定位可以消除的重复工作：fork 路径免去整份 lower 的 clean 数据复制及目录树遍历；相互独立的存储、网络与日志准备，其等待可由耗时之和缩为最长一项，节省量为“各项之和减去最长项”。实际收益须按依赖关系和关键路径核算，为后续指标分解提供可归因的依据。
