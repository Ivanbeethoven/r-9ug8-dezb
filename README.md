# CCF-蚂蚁科研基金（第二批次）项目申请书 — 交付说明

## 一、这份材料是什么

面向 **2026 年度 CCF-蚂蚁科研基金（第二批次）· 超算与智算方向**
课题 **《面向 AI Agent 沙箱极速冷启动的 Nydus EROFS 按需加载与 Checkpoint/Restore 机制研究》**
的完整项目申请书（约 1.4 万汉字，24 页，4 张图，13 张表）。

技术底座是团队主导的开源项目 **BrewFS**（Rust 分布式文件系统，github.com/brewfs/brewfs），
申请书把它的 workspace overlay（不可变 packed lower + 私有可写 upper + lease/generation fencing）
作为贯通 Nydus EROFS 镜像加载、工作区创建、快照恢复与并发创建的统一数据面。

## 五、文档结构

一、摘要 → 二、研究背景与问题分析（8 环节链路拆解 + 5 类开销 + 根本缺口）→ 三、研究目标与
关键科学问题（含三条指标的时间预算表与量化推演）→ 四、研究内容（4 项工作 + 三点创新）→
五、技术路线与系统架构（分层图、冷启动与 C/R 时序、关键数据结构、失败恢复、与蚂蚁栈对接）→
六、技术指标与评测方案（指标映射、缓存控制、消融、联调复现）→ 七、研究计划（12 个月、里程碑）→
八、研究基础与团队（履历、BrewFS 工程与性能数据、分工）→ 九、交付成果、预算、风险、知识产权。

## 六、写作口径（评审会看到的两个特点）

1. **所有性能数字都来自 BrewFS 公开实测**（2026-09-22 阿里云对齐评测、2026-11-02 写合并对比），
   目标值一律标注为"目标/待验证"，没有把预期写成既成事实。
2. **主动写短板**：随机写 p99 463ms、workspace overlay 仍是 opt-in feature、运维工具链未成熟，
   都写进了风险与优化目标——这类诚实表述在蚂蚁评审中通常加分。

## 八、第二轮修订（2026-11-05 晚）改了什么

按 PI 意见做了三处调整，改完重新导出了 docx/PDF（24 页，目录页码已回填）：

1. **定位前置**：摘要第一句改成"BrewFS 是团队主导研发、面向 Agent 负载的 Rust 分布式文件系统…"，
   第八章开头同样先立住身份。全文不再以 overlay 为主线词。
2. **术语去黑话**：`workspace overlay → 工作区隔离`、`packed lower → 只读基座`、`upper → 私有增量层`、
   `lease + generation fencing → 写者租约与代次校验`、`tombstone → 删除标记`、`copy-up → 写时复制`。
   英文原词只在首次出现时括注一次（`overlay` 全文仅剩 2 处，都是 cargo feature 名）。
3. **指标口径**：JuiceFS 对比前置到摘要与第八章独立小节，改用倍率表达——
   混合随机 I/O 约 2.5 倍、顺序写 +73.6%、写回排空 2–4 秒对 91–127 秒（约 30 倍以上）、
   总体 1.4–2.5 倍；删除了 p99 463.471/492.831ms、PUT/GiB 261,490.89 等不利绝对指标，
   短板改为定性表述（"写吞吐领先，前台尾延迟仍高于对照，已列入优化目标"）。

修订前的版本保留在 `sections.bak-20261105-1951/`，可用于对比或回退。
